# 版型契約

動筆前用兩篇已完整讀完的正式文章填寫。不要只寫「參考舊文」，要記錄實際共同 pattern。

```markdown
## 版型基準

- 基準文章 1：/absolute/path/to/article-1.md
- 基準文章 2：/absolute/path/to/article-2.md
- 選擇理由：同為產品比較文／節點教學／版本更新等

| 區域 | 基準共同 pattern | 目標文章做法 | 偏差 |
|---|---|---|---|
| Front matter | 欄位與 tags/categories 排版 |  | 無 |
| 開頭 | 封面、摘要、QuickNav 的順序 |  | 無 |
| Heading | H2/H3 與 anchor 寫法 |  | 無 |
| Custom Tags | quickNav/dataTable/faq JSON 排版 |  | 無 |
| 圖片 | 標籤、alt、資料夾與檔名 |  | 無 |
| 收尾 | FAQ、相關文章、參考來源順序 |  | 無 |
| CSS | 是否允許文章內 style |  | 無 |

### 矛盾 pattern

- 差異：
- 採用哪一篇：
- 理由：較新／同類文章使用較多／用戶明確指定
```

## 選基準原則

依序判斷：

1. 同一文章類型比主題字面相似更重要。
2. 同一交付形式比同一產品更重要。
3. 近期文章優先，但不能只因日期新就選不同類型文章。
4. 找不到兩篇完全同類時，選一篇結構相近、一篇 Custom Tag 與收尾相近，並記錄限制。

## 常見失敗

### 只讀一篇

單篇可能是例外或舊格式，不能推導共同慣例。必須讀兩篇。

### 只看 front matter 與 heading

這會漏掉 JSON 排版、圖片標籤、文章結尾、來源區塊與文章內 CSS。必須完整讀文。

### 先寫完才找基準

這會讓 review 變成事後補洞，通常會殘留混合格式。基準契約必須在動筆前完成。

### 用建置成功代替格式一致

Astro 能渲染單行 JSON 或文章內 CSS，不代表它符合這個 Blog 的既有做法。建置與版型是兩個不同 gate。
