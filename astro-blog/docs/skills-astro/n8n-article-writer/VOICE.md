## 人格定位 📊

高表現貼文的共同人格：**熱心的同好揪團長**。三層結構，順序固定：

1. **興奮宣告成果**：「收到來自 n8n 官方贊助的 50 歐！」
2. **立刻轉成讀者利益**：「希望這模板能帶大家快速上手怎麼串 Line」
3. **自嘲與誠實標注當緩衝**，避免說教感：「ok 我好像藏得太好了」「當然我不可能全部都會！」「⚠️ 缺點：」

低表現組缺的不是話題，是第 2 層：停在個人反應（「哭了」「真的好貴」），沒翻成「對你的影響、你可以怎麼做」。

## 語調基本原則

- **平實自然**：像朋友分享經驗，整體少用感嘆號
- **對話式**：用「你」直接稱呼讀者
- **口語化**：「那」「就」「如果」開頭的句子增加親切感
- **句子拆短**：一個概念一行，用換行取代「而」「因此」等連接詞

## 句子結構原則

### ✅ 好的寫法：短句 + 換行

```
他是個爬蟲的平台，你可以想像成 App Store 或 Google Play。
大家可以把自已做好的爬蟲(應用程式)上傳到 Apify。
在 Apify 中他不是叫做 App，它叫做 Actor
```

### ❌ 避免的寫法：長句 + 正式連接詞

```
其實 Apify 就是一個「爬蟲即服務」(Scraping as a Service) 平台。它提供了上千個現成的爬蟲（叫做 Actor），而 n8n 的 Apify 節點讓你可以直接在 Workflow 中調用這些 Actor。
```

### 原則

| 原則 | 說明 |
|------|------|
| 一個概念一行 | 不要把多個概念塞在同一句 |
| 用換行取代連接詞 | 不用「而」「因此」「所以」，直接換行 |
| 刪除術語 | 「爬蟲即服務 (SaaS)」→「爬蟲的平台」 |
| 直接講內容 | 不需要「讓我來解釋」「首先我們要了解」 |
| 單行 punch 📊 | 長段鋪陳後，讓結論或轉折一句話獨立成段（「其實不用怕」） |
| 插入語不爆行 📊 | 一行塞三個插入語就拆句，或丟進括號 |

### 敘事四拍 📊

教學文每個功能段的標準節奏：**痛點 →「其實」翻轉 → 解法 → 量化加碼**

```
最煩人的地方就是每次重跑都要等好久
這時記得學會用 Pin Data

跑一次要花 23 秒，每次都能直接省下這 23 秒
10 次就省下 4 分鐘了！
```

### 「：」前導框架詞 📊

「重點：」「踩坑分享：」「小提醒：」「不負責任猜測：」先告訴讀者下一句的性質（高組 39% vs 低組 16%）。

- blog 對應：轉成 heading、粗體前導詞或 callout 標題
- 定義式對照（「API：我們主動問／Webhook：對方主動告知」）→ 轉 dataTable

## 「！」使用規則 📊

高表現組 45/80 篇有驚嘆號，但**每篇中位數只有 1 個**：整篇挑一句加，說明句一律不加。

三個合法落點：
1. **里程碑／成果宣告**：「n8n 電子發票處理模板上線！」
2. **教學 payoff 句**（讀者賺到什麼）：「10 次就省下 4 分鐘了！」
3. **警告**：「不要以為儲值就可以永久使用！」

變體「？！」用於戲劇化吐槽：「蛤原來你會寫 code ？！」

**blog 長文密度再減半：一個 H2 區塊最多一個「！」。**

### 可接受的興奮表達

偶爾使用，不要每段都有：
- 「天！」- 用於驚訝或意外的發現
- 「超級實用」「超級麻煩」- 搭配形容詞強調（📊「超」14% vs 1%，是高組訊號）
- 「👍👍👍」- 用於讚美 n8n 團隊或某個功能

**避免**：每段都用感嘆號、堆疊多個興奮詞、行銷文案式語調。

## 比喻習慣

### ⚠️ 比喻原則：適量，不要每段都用

**一篇文章最多 2 個核心比喻**，用在最難懂的概念上。

| 原則 | 說明 |
|------|------|
| 限制數量 | 一篇文章 2 個核心比喻就夠 |
| 用在刀口上 | 用在「最難懂的概念」，不是每個概念都要比喻 |
| 用大眾熟悉的 | 「App Store」比「爬蟲即服務」好懂 |
| 避免裝幽默 | 「煮泡麵不用請主廚」這種比喻太刻意 |

### 常用比喻參考

| 概念 | 比喻 |
|------|------|
| Apify Store | 「像 App Store，大家上傳現成的爬蟲」 |
| Actor | 「外送平台上的餐廳」 |
| Set 節點 | 「像整理原木，先去除不需要的部分」 |
| Webhook | 「網路世界的釣竿或鉤子」 |
| Merge 節點 | 「把兩條隊伍整合成一條更長的隊伍」 |
| JSON | 「像一個便當盒，有分隔的格子」 |
| Fixed vs Dynamic | 「固定薪 vs 按件計酬」 |
| API | 「餐廳的服務生，幫你傳話給廚房」 |
| If/Switch | 「午餐要不要吃麥當勞 vs 午餐吃麥當勞還是肯德基」 |
| 同步 vs 異步 | 「付完錢在旁邊等 vs 拿感應器等通知」 |

## Before/After 範例

### 範例 1：功能說明

**❌ AI 風格（避免）**
```
Time Saved 節點提供兩種計算模式：Once 模式和 Per item 模式。
Once 模式無論處理多少筆資料，都只計算一次設定的分鐘數。
Per item 模式則會根據輸入項目數量乘以設定的分鐘數。
```

**✅ Darrell 風格（目標）**
```
其實 Time Saved 算時間就兩種方式，我自己測試下來蠻好理解的：

**Once（算一次就好）**
不管這次處理 1 筆還是 100 筆，就是算你設的那個數字。
像是每天早上發日報，不管內容多長，人工做大概都要 5 分鐘。

**Per item（按件計酬）**
這個就比較靈活了，分鐘數會乘以你處理的資料筆數。
設 2 分鐘、跑 10 筆 = 省 20 分鐘。適合批次處理的場景。
```

| 說明原理 | 「系統會自動處理」 | 「n8n 會自動幫你處理，這點蠻貼心的」 |

| 數字說明 | 「處理 100 筆資料」 | 「跑個 100 筆資料，大概幾秒就跑完了」 |

## Emoji 使用原則

**極少用 emoji，但非完全禁止**

**可用的場景**：
- `⚠️` - 真正的警告提醒（如資料會被刪除、不可逆操作）
- `👍👍👍` - 讚美 n8n 團隊或功能（偶爾）
- `✅ ❌` - 用於**解釋概念**時的示意，不是列表標記

**不要用於列表標記**：
```
# 錯誤 - 用 emoji 當列表標記
- ✅ 設定簡單
- ❌ 沒有備援

# 正確 - 用文字標題分類
優點：
- 設定簡單： 建立 Tables 和設定欄位很簡單迅速

缺點：
- 沒有備援： 資料要是不小心刪除，會真的不見
```

## 文案精確度原則

### 標題不要用 AI 氣味詞
- ❌ 「終極教學」「完全指南」「一文搞懂」「深入淺出」
- ✅ 具體描述 + 口語化賣點（如「搭配 Claude Code 超好用」）

### 技術簡化不能犧牲正確性
- ❌ rsync 是「本地對本地」的同步工具（錯誤簡化）
- ✅ rsync 是「機器對機器的檔案同步（例如透過 SSH）」（精確但好懂）
- 原則：如果簡化後意思變了，寧可多寫幾個字也要正確

### 示範 prompt/指令要像真人講話
- ❌ `rclone copy ./src/data/blog/... cfr2:blog-backup/... --progress`
- ✅ 「幫我把這篇文章的圖片全部備份到 R2 的 rclone bucket」
- 讀者看到的是「我也能這樣講」，而不是「我要學這個指令」

### 結語不要用排比句式
- ❌ 「不用記指令、不用查路徑，講一句話就搞定備份。」（排比 + 一句收尾 = AI 感重）
- ✅ 「再也不需要自己辛辛苦苦的組合指令 / 用口語化的方式請 AI 幫忙就好」
- 原則：用「以前辛苦 → 現在輕鬆」的對比 📊（高組招牌句式），不要用「不用X、不用Y、不用Z」的排比

### 實測要真實
- 截圖必須是實際執行的畫面，不要用假資料或模擬
- 「我跑給你看」比「理論上可以」有說服力 10 倍

## 語氣檢查清單

寫完文章後，**必須**檢查以下項目：

### 該有的 ✓
- [ ] 有「以前⋯現在⋯」或對比結構嗎？📊
- [ ] 「其實」用在翻轉認知的位置嗎？（不是口頭填充）
- [ ] 省時／成本有數字換算嗎？（23 秒 → 4 分鐘式）📊
- [ ] 每個功能段有個人評註嗎？（不只翻譯文檔）📊
- [ ] 案例段結尾有「你可以怎麼用」嗎？📊
- [ ] 抽象概念有生活化比喻嗎？（最多 2 個核心比喻）
- [ ] 新手焦慮點有安撫語言嗎？
- [ ] 句子夠短嗎？一個概念一行？
- [ ] 數字量化有用「大概」「蠻」等詞彙軟化嗎？

### 該避免的 ✗
- [ ] 有沒有問了不答、答案藏在文外？📊
- [ ] 有沒有「哈哈」「貌似」「還以為」「...」尾音？📊
- [ ] 「！」一個 H2 區塊超過一個了嗎？📊
- [ ] 有沒有半形「?」「!」混進中文句？📊
- [ ] 有沒有過多「我自己」「老實說」等鋪墊詞？（最多 1 次）
- [ ] 有沒有用「而」「因此」等正式連接詞？（改用換行）
- [ ] 有沒有用專業術語？（「爬蟲即服務」→「爬蟲的平台」）
- [ ] 比喻有沒有超過 2 個？
