### 2026-04-20：改外部服務文章前沒 reconcile 官方 docs

**背景**：改寫 `n8n-bycrawl-node.md`，3/19 舊草稿仍留在 working dir

**問題**：
- 草稿裡 TikTok「留言 90 pt、分類瀏覽 210 pt」的警告是整篇賣點之一
- 對照官方 API docs 後發現：TikTok 留言只要 3 credit、沒有「分類瀏覽」端點
- 如果不驗證直接發，整篇的「TikTok 很貴」警告都是錯的

**教訓**：
1. 改寫談外部服務的文章前，**平行跑兩個 agent**：
   - A agent 掃該服務的 project memory（過去實測踩坑）
   - B agent 抓官方 docs 最新版本（API、定價、操作清單）
   - 完成後 reconcile 兩邊資訊，再動手改
2. 供應商的「行銷數」和「API 數」常常對不上（例：ByCrawl 官方「15 平台」vs API reference 列出 18 prefix），寫文章前先選好要採哪個口徑
3. 重大事實差異（如定價誤差 30 倍）要先跟用戶確認走向，不要直接信任舊草稿

### 2026-01-10：GEO 模組化 A/B 測試

**背景**：測試「40-60 字模組化段落」是否能改善 AI 搜尋排名

**測試方法**：10 位模擬讀者（5 初學者 + 5 中階者）

**問題**：
- 把「適合場景」列表拆成「適合X。適合Y。適合Z。」
- 多位讀者評價：「像 AI 產的」「很機械」「要自己在腦中重組」

**原因**：
- 機械式套用「模組化」建議，沒有區分內容類型
- 沒有在修改後測試人類閱讀體驗

**教訓**：
1. 列表本身已是好結構，不該再拆
2. 口語詞（其實、老實說、蠻）是可讀性潤滑劑，拆句時容易一起拆掉
3. 比喻要完整展開 + 括號對照技術概念
4. 任何格式變更都要先讓人讀過一遍

## GEO（AI 搜尋優化）

### ✅ 適合模組化的內容
- 參數說明：每個參數獨立一段，方便 AI 提取
- 定義句：開頭用一句話定義概念（blockquote 或粗體）
- FAQ 答案：Answer-first 寫法

### ❌ 不該模組化的內容
- 列表內容：保持列表格式，不要拆成獨立句子
- 比喻段落：需要完整展開 + 括號對照技術概念
- 操作步驟：保持編號，讓讀者知道「共幾步」
- 敘事段落：保持自然語流和連接詞（其實、但、所以）
